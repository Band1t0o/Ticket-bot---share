Operating manual

Finding a cheap way to fly a trip with several stops

You give it a date window, a handful of airports you could leave from and the places you want to go. It searches, night after night, and tells you what the whole trip costs and when it gets cheaper. This is how to drive it.

GETTING STARTED

Setting it up

Four things have to be in place. The fourth is the one that is easy to miss and stops everything working.

  1. Python 3.12. Then make install in the repo folder, which builds a virtual environment and pulls the dependencies.
  2. A browser for the scraper. make pw-install downloads the Chromium that Playwright drives. It is a large download, once.
  3. A GitHub repo of your own holding this code, with Actions enabled and its workflow permissions set to read and write. That setting lives under Settings, Actions, General, and without it the nightly search cannot commit what it found.
  4. The GitHub CLI, installed and signed in. Install gh, then run gh auth login once.
Why the GitHub CLI matters

Every button that starts a search asks GitHub to run it, and the app asks through gh. Without it the buttons fail and the cloud panels say they cannot tell what is happening. Nothing else in the setup has that effect.

Starting it

On Windows, double-click start-ui.bat. It finds the virtual environment, starts the server and opens the browser at http://localhost:8000. Closing that window stops the server. On anything else, make ui does the same thing.

The page opens on an example trip so there is something to look at: Vienna to Tokyo, across Japan overland, on to Cebu, home again. It is switched off, so nothing will search it. Edit it into your own trip, or press + New trip and delete the example once you no longer need it.

THE ONE RULE

The searching does not happen on your laptop

This is the single fact that explains the shape of everything else. The site being searched answers about 120 searches from one internet connection and then goes quiet. Not slower. Silent. A thorough search of a three-stop trip is three to five hundred searches, so it can only be done by splitting the work across several machines at once, and that is what GitHub Actions is for.

So every run button hands the job to GitHub. Your laptop can be shut the whole time. When a run finishes it writes what it found into the repository as a commit, which is how the results get back to you.

The bar at the top of the page

Because results arrive as commits, your copy of the folder falls behind. A strip appears above everything saying how many runs are on GitHub but not on this machine. Get them pulls them down normally. Just get the results appears instead when a plain pull would be messy: it copies only the result folders and leaves your own work alone.

One consequence worth knowing early: the trip is searched as it is saved on GitHub, not as it looks on your screen. Every save publishes the trip up, and if the two ever disagree a run is refused with a message naming what differs. That is deliberate. Searching a version of the trip you cannot see would waste an hour and tell you nothing.

MONEY

Keep the repository public

GitHub gives unlimited Actions minutes to public repositories and 2,000 a month to private ones. The schedule below is comfortably free on a public repo and does not fit in 2,000 minutes on a private one.

What runsWhenPer day
Full sweep02:00 UTC, every trip you ticked on1
Narrowed sweep13:00 and 20:00 UTC, only if you asked2
Price checkevery four hours, only what you follow6
Volatility probeships switched off0
The trap

A scheduled run costs a minute or so even when it decides to do nothing. Nine wake-ups a day is around 270 minutes a month before a single flight has been searched, and the searching itself is far more. Untick every trip and that cost does not go away, because the schedule is still running. Turning it off properly is its own section.

Public means the trips you plan and the prices you find are readable by anyone who finds the repository. That is the trade. If you would rather it were private, the workable pattern is to plan the trip in the open, book it, pause the schedule, and only then make the repository private, where it costs nothing because nothing is running.

One more thing about schedules

GitHub switches scheduled workflows off by itself after 60 days without activity in the repository. If sweeps stop for no apparent reason after a quiet couple of months, that is usually why, and the panel under the gear will say so rather than just showing them off.

PHASE 1

Cast a wide net

The situation this is built for: there is a stretch of weeks you could travel in, several airports you could plausibly leave from, and a rough idea of where you want to go. You do not yet know which combination is affordable. Phase one is about finding out cheaply, before committing hours of searching to options that were never going to work.

Your airports

Start under the gear, in Your airports. This is a ranked list of the airports you can actually get to, easiest first, and it is about the journey to the airport and nothing else. Not price. Not how often you have used them. Two airports that are equally awkward go on the same row, because forcing an order on them would invent a preference you do not hold.

It does two jobs. It becomes the one-click suggestions beside every airport box, and it is the order Discord reports in. You can still type any airport in the world; this only decides what is offered without typing.

Building the route

Go to Map it out, sub-tab Search options. The When panel takes the trip name, the window the whole trip has to fit inside, how many of you there are and the currency. Make the window generous. Narrowing comes later and is easy; a window that was too tight from the start quietly hides the answer.

The Route panel reads top to bottom, the way you would travel:

  • Depart from takes as many airports as you are willing to leave from. Type a city, a country or a three-letter code and press Enter. Each one you add multiplies the searching, so add the ones you would genuinely use.
  • Each stop is a numbered card: what to call it, how many nights you want there as a range, and which airports would serve. Several airports on one stop means "whichever is cheapest".
  • Arriving and leaving by different airports is the checkbox on a stop card with two or more airports. Tick it for the classic case of flying into one city, travelling across the country yourself, and flying onward from another. You then pin which is the way in and which is the way out.
  • Return to is how the trip ends. Leave it matching your departure airports for a normal return trip, change it to end somewhere else, or empty it entirely for a one-way. There is no separate one-way switch.

Press Save trip. Nothing is searched by saving.

Running a probe

The Run panel has one button per kind of run, each showing what it will cost in searches and minutes before you press it. Start with Probe.

A probe is the cheap reconnaissance run. Rather than pricing every date, it prices every route on three dates spread across your window, which is enough to rank airports against each other. Fifty-odd searches instead of five hundred. It is the difference between a couple of minutes and most of an afternoon, and it answers the question phase one is actually asking: which of these options are worth the expensive search?

What a probe will not do

It never changes your trip. It reports, and you decide. It also never gives you a fare you could book — three sampled dates are a floor to compare airports by, not a price.

PHASE 2

Cut it down

Now throw away what does not work. This is where a trip goes from twelve plausible combinations to two or three real ones, and it is worth doing properly, because everything after this is slow.

Reading the verdicts

The Probe results sub-tab, headed Worth searching?, is one row per airport, grouped by the job it does in the trip: your departure airports together, each stop together, the return together. Each airport is judged only against the others that could do the same job.

VerdictWhat it meansWhat to do
best Cheapest of its group Keep
close Within 15% of the best Keep — on other dates it may win
worse Up to 50% over Your call, and it costs searching
poor More than 50% over Drop it
no offers Asked several times, answered, nothing on sale Drop it. Real absence of flights
unproven The site never answered Not a finding. Probe again

The last two look similar and mean opposite things. no offers is information: that airport genuinely sells nothing on that route, which is common for convenient regional airports and is exactly the kind of thing worth writing down so you do not reconsider it in six months. unproven is an absence of information.

Each row has Remove from trip. There is also Keep probing it, which takes an airport out of the expensive searching but keeps sampling it cheaply — useful for the one that was close but not close enough, in case it moves. Removals gather in a bar at the bottom with Undo, so deciding about six airports is one pass and one save rather than six rounds.

Sweeping properly

With the field cut down, search for real. Back on Search options, the Run panel offers two:

RunPricesUse it
Quick sweep Every 7th day of the window To see the shape of the window fast
Deep sweep Every single day When you are choosing actual dates

A deep sweep takes a couple of hours in the cloud. Start it and go away; you are not waiting on it. The nightly schedule always runs at full depth regardless of which button you last pressed.

Reading the results

The Search results sub-tab shows one run two ways, and they answer different questions.

The charts, one per leg

Every flight, priced on its own stacks one chart per leg on a shared date axis, each with a marker you drag. A vertical slice down the stack is one whole trip. Drag the first leg later and the ones below it follow. Above the charts a readout gives the total including bags, how the nights divide up, and a badge saying whether that combination obeys the rules you set or breaks one and how.

Nothing is forced on you. You may drag into a combination that breaks your own stay ranges, and the badge will say so rather than refuse. The only thing actually prevented is a leg departing before the one before it has landed.

Snap to the cheapest that fits jumps every marker to the cheapest combination that obeys every rule. It is usually the fastest way to see what your constraints actually cost you.

A date with a small tick on the floor was searched and sold nothing. A date with a gap in the line was never searched. Those are different, and the charts keep them apart.

The ranking

Below, the same run as a sorted table: cheapest first, with the route, dates, airlines, whether bags are included, and the total. Filter by departure airport, by return airport, or to only fares that include baggage. Expanding a row shows each flight on its own with times, airline, a link that opens the actual offer, and a Follow button.

Every price carries its age

Fares move. Nothing here is presented as current without saying when it was measured, and a run too incomplete to compare fairly is never drawn as part of a trend. If a warning says coverage was below 100%, the site refused some of the searches and the cheapest shown may simply be the cheapest of what got through.

PHASE 3

Settle on one, then watch it

You have a shape you like: roughly these dates, roughly this long in each place. Now stop searching the whole window and start watching the thing you actually intend to book.

Narrowing it down

The Narrow it down step has three controls and they are independent:

  • Leave between bounds the first flight out.
  • Fly home between bounds the last flight back.
  • The nights chip bounds the whole trip, for example 24 to 28 nights away. Clear it with its small ×.

Per-stop stay lengths are here too. A line above the buttons always spells out, in plain words, what these dates are currently doing, because they do two separate things: they filter what you are reading on this step, and they define what the narrowed sweep searches. A combination nothing could satisfy is refused by name rather than silently returning nothing.

Sweep narrowed prices only what you narrowed to, which is a fraction of the full window and therefore quick enough to run twice a day. Everything below on this step is drawn from narrowed runs only, never mixed with the broad ones.

Following a price

Two things can be followed, and the Follow it step keeps them separate.

A preference — the whole trip, on dates you picked

From the charts, drag to the combination you want and press Save as preference. From then on, every four hours, that exact trip is re-priced and plotted. You get up to four, each with a slack setting: exact days, or anything up to three days either side. Slack is what lets it tell you that leaving a day later would have been cheaper, which appears as a sentence under the row with a Move it to those dates button. Moving keeps the history rather than restarting it.

A followed flight — one leg

The Follow button on any single flight. One search per check, so it is cheap, and it is the right tool when only one leg is the problem — the long-haul that dominates the total while the short hops barely move.

A summary line at the top of the step says exactly what you are spending: how many searches every four hours, for both panels together. Nothing here changes when you edit the trip or the narrowing. What you chose to follow stays followed until you say otherwise.

The long view

Best total over time plots sweep against sweep. Only runs that finished and covered every route the trip currently plans are joined into the line; the rest are drawn hollow and dashed and never called the best. Broad and narrowed runs are two separate lines, because they are measuring different things and averaging them would be meaningless.

NOTIFICATIONS

Discord

Optional, and the only notification channel. In a Discord server you can manage, open a channel's settings, Integrations, Webhooks, create one and copy its URL.

Paste it under the gear, in Discord, and press Save webhook, then Send a test message. It is stored in a .secrets folder that is never committed. For the scheduled runs, which happen on GitHub and cannot see your laptop, add the same URL as a repository secret: 

gh secret set DISCORD_WEBHOOK_URL -R <your-user>/<your-repo>
Treat the URL as a password

Anyone holding it can post to that channel. Never commit it, never paste it into an issue. If it leaks, delete the webhook in Discord and make a new one.

You choose what gets sent: the cheapest trip overall, the cheapest from the airports you prefer, or only when something beats the best price seen so far. That last one is the difference between a useful message and a nightly one you learn to ignore. A followed flight is only reported when it drops by more than one percent.

WINDING DOWN

Stopping everything

When the trip is booked, you want it all to stop. There are two separate levers and it matters which one you reach for.

Taking one trip out of the rotation

In the schedule dialog, reachable from Scheduled sweeping, untick Sweep the whole window, nightly. That trip stops being swept and stops being checked. Other trips carry on. Use this when you are done with one journey but still planning another.

Stopping the machine

Under the gear, in The cloud, is a line saying what is currently scheduled and roughly what it costs a month, and one button: Pause all scheduled runs.

This switches the scheduled workflows off in GitHub itself. Not "wake up and do nothing" — genuinely off, starting nothing and costing nothing. It leaves every trip exactly as it was, so Resume scheduled runs brings back the same schedule later. Runs you start by hand still work while paused.

Making the repository private

Pause first, check the panel says nothing is scheduled, then change the repository to private. In that order it costs nothing. In the other order the schedule starts eating your 2,000 free minutes the same night.

The panel also distinguishes a pause you made from GitHub switching a workflow off after 60 days of quiet, because otherwise those look identical and only one of them is something you did.

Stopping a run that is going now

Stop this run, in the strip at the top of the page. It finishes the search already in flight and keeps everything found so far rather than throwing the run away. If a stopped or interrupted run left part of its plan unsearched, a Resume button appears to finish it.

TROUBLESHOOTING

When it looks wrong

What you seeWhat it means
The page says to restart the server The running server is older than the page it is serving. Restart it. This is deliberate: an empty page must never be mistaken for lost data.
"The site is refusing this client" The rate limit. The run pauses, backs off and, if it continues, ends as throttled and records honestly how much it covered. Not a bug and nothing to fix. Try later.
A run finished in seconds and looks successful It searched nothing. Usually the trip on GitHub is not the trip on your screen, or the run asked for something that trip cannot do. The recent runs list flags these.
Coverage below 100% Some searches went unanswered. The cheapest shown is the cheapest of what got through, which may not be the cheapest there was.
Panels say they cannot tell gh is missing, not signed in, or offline. The schedule on GitHub is unaffected; only this app's view of it is.
Nothing has run for weeks Check the gear. Either the schedule is paused, or GitHub switched it off after 60 days of quiet, or no trip is ticked on.
Prices look wrong across the board The site changed its markup. Under the gear, Where the prices come from has Check them all, and a repair box exposing the selectors.

python -m src.cli check-price --origin VIE --destination HND --date 2027-01-12

The volatility probe

A small extra that answers "how fast do these fares actually move", by sampling a few fixed routes every couple of hours. It is what established that fares move day to day rather than within a day, which is why sweeping nightly is enough.

It ships switched off and with no routes, for two reasons. Its routes are fixed rather than read from your trip, so that months of observations stay comparable, which also means inherited routes would measure someone else's journey. And every two hours is about 720 Actions minutes a month: free on a public repo, more than a third of the allowance on a private one. To use it, put your own routes in src/probe.py and add a schedule back to .github/workflows/probe.yml. The comments in both files say how.
